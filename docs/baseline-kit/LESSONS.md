# Failure shapes

Not a style guide. A catalogue of the specific ways things have gone wrong, each with a real
instance and the guard that now prevents it.

**Every one of these shipped, or nearly did, with a green build and passing tests.** None was a
crash. That is the point: the failures worth cataloguing are the ones where the code runs, the
tests pass, the numbers look plausible, and the answer is wrong.

Read this before a codebase review, and look for these shapes specifically rather than for "code
smells".

---

## 1. The path under test is not the path that ships

**The most common shape by a distance.** Tests are written against a helper, an accessor, or an
inline decision that no production code actually calls. They pass forever and guard nothing.

**Instances:**

- Two tests named for checking that a runner showed the right text called an accessor **no front
  end had ever called**. Both surfaces called a different function. Discovered a milestone later,
  by grep.
- A decision made inline inside a function that needs a hardware device. Reverting it compiled
  cleanly and broke **no test**, because nothing in a suite can reach inside that function.
- A test asserting a pattern builder produced the right output, while the code that *used* the
  builder was free to ignore it.

**Guard:** before writing a test, ask what production code calls the thing you are about to
assert on. If the answer is "nothing", you are testing a copy. When logic sits inside something
untestable, **move the decision out** to a property or a small function the suite can reach —
then revert it and check the test fails.

---

## 2. A guard verified by reading it

A validation rule, lint check or assertion that looks correct and matches nothing.

**Instances:**

- A pattern intended to catch unchecked unwrapping matched only one of the two syntaxes. Eleven
  violations sat under a green pass.
- Its replacement was broken the same way — a character class that closed early, so the pattern
  meant something else entirely and matched nothing. **Two rounds of checking at the shell missed
  it**, because the shell and the script disagreed about escaping.
- A "does everything still load" check ran a command that printed a warning and exited zero, so
  the gate could never fail. It also only loaded one of six record types.

**Guard:** plant a violation, watch it report failure, remove it, watch it pass. Do this for every
rule, at the time you add it. Reading the rule is not verification, and neither is testing it in a
different shell.

---

## 3. A filter that hides real hits

A search narrowed to reduce noise, which then conceals the thing being searched for. Especially
dangerous because the *result* of the search becomes a claim in a document.

**Instances:**

- A search for unchecked unwrapping excluded lines containing a quote, to duck string-literal
  false positives. That filter hid five real violations, and the count went into a review as six
  when it was eleven.
- A survey of a type's consumers excluded filenames containing a word, to suppress noise. It hid
  a real consumer, and "this has exactly one consumer" went into a design document. It had two.

**Guard:** when a filter is needed, report what it excluded. If a search result is going to become
a claim, run it unfiltered once and read the noise.

---

## 4. A test that compares the system against itself

Asserting that output matches a value the same code produced. It passes through any mistake made
consistently.

**Instance:** a test that a fixed parameter "never moves" compared each result against a reference
generated by the same function. Changing the underlying constant moved both sides together and the
test passed. It could detect variation *between* runs and was blind to a constant that was simply
wrong — which is the likelier mistake.

**Guard:** assert against values stated independently — arithmetic written longhand in the test, a
figure computed by hand, or output captured *before* the change. When rewriting a computation,
capture the old output first and diff it.

---

## 5. A test that only runs the easy case

The configuration where the bug cannot appear.

**Instance:** a test that feature A never displaces feature B ran only at the largest size, where
both fit and the ordering between them is unobservable. A change silently dropped B from **every**
small configuration. The test passed throughout.

**Guard:** identify the configuration where the behaviour is *observable* and test that one.
Usually the smallest, the most constrained, or the boundary — not the comfortable middle.

---

## 6. A derived unit that is not comparable across its own range

A ratio, percentage or normalised score that is meaningful at one end of an axis and misleading at
the other. The numbers stay plausible throughout.

**Instances:**

- A ratio whose sensitivity to its input ran from 4× to 16× across the useful range. Reporting its
  spread would have made identical steadiness look four times worse at one end — penalising the
  user for the very thing being trained.
- Dividing a measure by an interval to make it "comparable across speeds", on the assumption that
  it scaled with the interval. **It did not**, and the normalisation introduced the dependence it
  was meant to remove. The assumption had been stated as fact in a design document three times
  before anyone measured it.

**Guard:** before normalising, ask what the invariant actually is — and *measure* it rather than
assuming. Where two candidate units exist, report both and let the data say which is flat. Prefer
the unit that is linear in what the user physically does.

---

## 7. A cached summary nobody reads back — until someone does

A denormalised value kept "for legibility" that a caller eventually trusts.

**Instance:** stored summaries predating a fix were plotted by three separate views, so charts
showed values no current analysis produced, and a trend was fitted through the difference.

**Guard:** store raw inputs and recompute everything. If a cache exists, have the gate fail on
reads of it outside the writer.

---

## 8. Rounding without checking how far you moved

Snapping an observation to the nearest legal value, with no check that it was near one.

**Instance:** a produced quantity was divided by a target and rounded to the nearest whole number
to identify which multiple it was. At 1.45 it rounded to 1 and reported the result as **45% in the
wrong direction** — the same observation supports two readings that disagree about the *sign*, and
the code picked one and printed it as fact.

**Guard:** after snapping, check the distance. If the observation is not near a legal value, say it
cannot be read rather than choosing.

---

## 9. A constant that happens to match

Two places holding the same value for different reasons, agreeing only by coincidence.

**Instances:**

- A value derived from an object's property in one place and written as a literal in another. They
  matched because a default happened to equal the literal. The first non-default configuration
  would have silently changed every stored record's meaning.
- A threshold that existed in **three** copies while a design document claimed it had been
  consolidated into one. Two of the three were literals.

**Guard:** derive from one source structurally rather than keeping copies in sync. When
consolidating, grep for the *value* as well as the name — and see shape 3 about the grep.

---

## 10. One word, two meanings

A term that means two different things in one codebase. Every use is a coin flip.

**Instance:** "how finely we divide the beat" legitimately meant both *how finely the content is
authored* and *what the user is scored against*. They coincided at one value for a year. Once
they diverged, the ambiguity produced **four separate defects in a single milestone** — including
one written directly beneath a comment explaining the distinction.

**Guard:** rename one of them the moment you notice, even if nothing is broken yet. Put the
distinction in the parameter name, not only in a doc comment — comments do not get read at the
call site.

---

## 11. The threshold you reasoned to is wrong

A limit chosen by argument that is obviously wrong the first time real data goes through it.

**Instance:** a minimum sample size of 8 was chosen because that is what the statistics require.
On real data, 12 observations against 117 produced a confident claim about a systematic behaviour
— from twelve incidental events. Enough for the arithmetic, nowhere near enough to be the thing
being described. The fix needed a *second, different* guard (a proportion, not a count), and the
count alone had passed the case that prompted it.

**Guard:** wire the readout to real data before believing the thresholds. Unit tests will not
catch this because they use data you designed.

---

## 12. Unchanged code failing

Tests fail on files a diff shows untouched.

**Instance:** twice in one milestone, after adding a stored property to a shared type. Test objects
were still compiled against the old memory layout. Both times the failures pointed at unrelated
logic and looked like real bugs.

**Guard:** when a failure is in code you did not change, clean the build before debugging. Cheaper
than the wrong investigation, every time.

---

## 13. A default that is not the identity

Treating "absent" as "the common value". Sometimes right, sometimes it erases a real distinction.

**Instances, deliberately opposite:**

- Absent *setting A* had to mean "nothing was prescribed", **not** the most common value — because
  "play freely" and "play this specific way" are different tasks that would have pooled into one.
- Absent *setting B* genuinely did mean the neutral value, because that value is the mathematical
  identity and every existing record truly was it.

**Guard:** for each optional field, decide explicitly which it is and write the reason beside the
field. If the default is an identity — an operation that provably changes nothing — absent may
mean it. If it is merely common, it may not.

---

## 14. A flag every caller must remember

Returning a value alongside a boolean saying whether to trust it.

**Instance:** a derived value was computed in three places with a "reliable" flag. Two callers
checked it. The third was found only because a trend that should have moved did not.

**Guard:** withhold at source. Return nothing when the value cannot be trusted, and report the
components that *are* honest separately.

---

## 15. Optional stopping

Recomputing a comparison after every new observation and reacting when it looks decisive.

**Instance:** a system that re-ran its analysis after every session would have been running the
same comparison dozens of times and keeping whichever answer it liked.

**Guard:** declare the target and the stopping rule before collection. Below target, compute no
verdict at all — withholding a number that has already been computed is still optional stopping,
because it is sitting there to be looked at.

---

## 16. A broken probe reporting a defect that is not there

The diagnostic is wrong, not the code.

**Instance:** an onset detector that fired on energy *tripling* found nothing after the first
event of a bar, which looked exactly like a feature never reaching the output. The feature was
fine. Two minutes were spent about to report a bug that did not exist.

**Guard:** validate the probe against a case whose answer you already know, before trusting it
about a case you do not. When a probe says "nothing happened", suspect the probe first.

---

## 17. The document that says more than the code supports

Prose drifting from the system it describes — the failure mode of a project that documents well.

**Instances:**

- An operating manual pointing at the second-most-recent findings, introduced *by* a pass that
  updated the table above the sentence and not the sentence.
- A paragraph stating a range and then contradicting it two sentences later.
- A design document claiming a consolidation that had not happened, for two milestones.
- Test and record counts copied forward unchecked across four separate accuracy passes.

**Guard:** documentation is a closing step of every change, and figures quoted in prose are claims
like any other — re-derive them from the system rather than trusting the previous value. Where a
document makes a checkable claim, prefer one a script can check.

---

## 18. A guard on a count cannot protect a variance

A gate that admits a *proportion* of bad observations, protecting a statistic that squares them.
The gate is not too loose; it is measuring the wrong thing.

**Instance:** a gate admitted a trial with up to 25% of its intervals outside a plausibility band —
the right question for *"was this a valid attempt at all"* and the wrong guard for a decomposition
that is **quadratic in the residuals**. Nine observations out of 232, **4%, comfortably inside the
gate**, carried up to **99% of a trial's squared error** and produced a figure five times any other
on record, displayed as reliable. Tightening the fraction would not have fixed it and would have
thrown away good trials.

**Guard:** match the guard to the *algebra* of what it protects. A count or a fraction protects a
count; a variance, a least-squares slope or anything else quadratic needs the outlier removed
rather than tolerated — and removed where the violation is, which is usually a boundary in the
data rather than a bad sample. Report what was excluded: an exclusion nobody can see is
indistinguishable from quietly dropping the data that spoiled the answer.

---

## 19. A confound named rather than separated

Printing a warning beside a verdict, and printing the verdict anyway.

**Instance:** a trend readout fitted one line per task with a caveat under it. Pooled across a
difficulty ladder one metric read **worsening** with an interval excluding zero; fitted on the one
difficulty level with enough points it was **flat**. Two verdicts were retracted on that basis, and
both were the ladder rather than the subject. In a separate case a single take of a different drill,
pooled into a group of twenty-one, turned that group's verdict from flat to worsening on its own —
and the mixed-inputs warning fired correctly throughout.

**Guard:** naming a confound is the floor; separating it is the fix. A reader who sees a verdict
and a caveat has still been shown a verdict. When an axis makes two observations a different task,
give it its own **group** — and keep one list of what those axes are, so two readouts cannot
disagree. The honest cost is that most groups then have too few points to say anything; they could
not say anything before either.

---

## 20. The error path discards the most diagnostic data

A failure mode that fires exactly when the observation went badly — so the data being lost is the
data worth having.

**Instance:** the encoder refused a non-finite number, and the analysis wrote one whenever too
little was captured to compute a summary. A record **failed to save** during a live session and is
gone. Three of five record types were exposed, and in every case the trigger was the run going
badly: too few events to average.

**The inversion is what makes it serious.** The records destroyed were the most diagnostic ones in
the set, and the surrounding manifest logged the block as *"skipped"*, so nothing downstream could
tell a destroyed measurement from a declined one.

**Guard:** every stored summary goes through a finite-or-nil helper, and the affected fields are
optional. Structurally: every stored type gets a round-trip test *with the type*, not after the
first record is lost — and when writing an error path, ask what the *worst* input looks like and
whether that is the input you most wanted to keep.

---

## 21. A rule nobody is stopped from breaking

A rule that is correct, written down, agreed — and enforced by nothing. It holds while somebody is
paying attention and stops the first time an afternoon gets productive.

**Instances, and a project keeps rediscovering this one:**

- *"Do not promote onto something nobody has heard"* was prose for a whole milestone. It became a
  flag with a safe default, beside a test asserting the current state, so approving something is a
  decision that arrives in a diff.
- *"Re-derive figures quoted in prose"* was in the definition of done through **five** documentation
  passes, each of which found counts copied forward unchecked. The fifth added a gate rule rather
  than a sixth reminder.
- *"A branch covers a coherent piece of work, not a single commit"* was in the standard from the day
  it was written, and was broken **nine times running**. Nobody noticed while it was happening,
  because nothing was watching.

**The tell is uniform**: the rule reads as advice, the cost of ignoring it is diffuse and lands
later, and whoever breaks it is being productive rather than careless. That is precisely the
combination discipline does not survive.

**Guard:** when a rule matters, ask what stops it being broken — and if the answer is "remembering",
build the smallest thing that says no. A flag whose default is the safe answer, a gate rule, a
refusal with the acknowledging option beside it. Where a rule genuinely cannot be mechanised, say so
where the rule is written, so its readers know they are the enforcement.

**And the acknowledgement is the design.** None of the three forbids the thing: the item can be
approved, the figure can be quoted, the branch can be one commit. What each removes is doing it *by
default* — the exception costs a deliberate act that shows up in a diff or on a command line.

---

## 22. The readout was fixed and the decision was not

A confound is found, and fixed in the thing that *displays* the data. The thing that **acts** on the
same data reads it unfiltered and nobody looks, because it prints nothing.

**The asymmetry is the whole shape.** A wrong readout shows a wrong number, and somebody eventually
reads it and asks. A wrong decision changes what the tool does next — what it schedules, what it
offers, what it withholds — and there is no line of text anywhere to notice.

**Instances:**

- A category of measurement was pooled into a comparison it did not belong in. It was found twice
  and fixed twice, both times in a readout: once in a trend line, once in a chart. The component
  that *scheduled the next piece of work* built its input with a `map` over every stored record, so
  the same confound went straight into the estimate that gated which options were offered at all.
  Two of those options had already disappeared from a picker with nothing saying why.
- A reliability flag was checked by the report and by the history chart, and **not** by the
  scheduler. It was found only because a trend that should have moved had not.

**Guard:** when a confound is fixed in a readout, ask immediately **what else reads the same
corpus** — and specifically what *decides* something from it. Then make the distinction structural:
one accessor carrying the argument, not a filter each caller remembers to apply, which is shape 9's
guard pointed at a predicate rather than a constant.

**And the tell is that the fix felt complete.** Both earlier fixes closed with a test, a document
section and a green gate. What neither asked was who else was holding the same list.

## Adding to this file

When something goes wrong, ask whether it is an instance of a shape above or a new one. If new,
add it at the end, **numbered next and never inserted** — the numbering is an interface. Give it
the shape in one line, the real instance with its numbers, and the guard. If it is an
instance of an existing shape, **add it there** — a shape with four instances is a much louder
warning than four separate entries, and shapes 1, 2 and 9 earned their place by recurring.
